# VISUALS -- seeing levels the way Geometry Dash draws them

Owner: the "visuals" session (2026-11-23). Goal: no session decorates blind. The viewer draws a level with
GD's own sprites from the user's install, and a catalogue shows what every object id looks like.

## Rule: RobTop's art never leaves the user's PC

The sprite sheets, backgrounds and icons are read at run time from the game's `Resources` folder by
`tools/serve.js` (`GET /gdres/<file>`, `/gdres/icons/<file>`; `GD_GAME` overrides the Steam path). Nothing
of the art is copied into the repo, onto the phone page or into an Artifact. Rendered pictures of it
(`local/shots/`, `local/catalogue/`) live in the never-committed `local/`. Committed are only facts:
object id -> frame names, offsets, colour roles, layers.

"GD art (not found)" in the viewer: the page could not fetch `/gdres/`. Seen 2026-11-23: the user's
`serve.js` on 8765 had run since before `/gdres/` existed (a node server keeps the code it started with),
so every sprite was a 404. Check `curl -s -o /dev/null -w "%{http_code}" localhost:8765/gdres/GJ_GameSheet-uhd.plist`;
404 -> restart serve.js from the main checkout. The button's tooltip names the file that failed.

Jump indicators (arrows 132/460/494 and 2.2's 3630-3632) and text (914) are drawn in every view, not
only with GD art: the shapes look draws them in `lib/look.js` `drawMark` (own shape, channel 21, group
alpha), the schematic view soft white. Other decoration stays out of the shapes look.

The button band -- its own canvas under the level (`#inbar`), never over the playfield (the user: "the timings
again are part of the ui and are annoying. put the timings below the level"; soft rule: UI never draws over the
playfield) -- shades each input's whole timing window, from the
earliest to the latest tick that works (presses cyan, releases pink, a tap's release moves with its press),
with its length in ms under it; the white mark inside is where the replay presses. The window is a player's
(`lib/windows.js` -> lib/difficulty.js measureWindows: later inputs re-planned, the one definition score.js and
difficulty use too). Saved and natural replays carry no windows, so the page works them out after the level
shows, in a Web Worker (`viewer/windows_worker.js`, shipped on the phone page too): one input can take 3.7 s,
which froze the page when it ran there. ~40 s for GDLM 45 on the PC, filling in as it goes; the click table's
window column fills when it is done. A level with no saved solution in viewer/levels.js is solved in the page
first (minutes, page frozen): `node tools/solutions.js <level>`, then `node tools/index_levels.js`.
`node tools/shoot.js <level> --input` stamps the band under headless shots.

Beat lines (viewer, every look): from `local/beats.local.js`, built by `node tools/beats.js` (or `--index` from
the analysed songs in local/beats/). It used to be written into viewer/ of whichever worktree ran it, so the
user's viewer (main checkout) had no beat lines at all; the phone build reads the same file.

## What is built

- **Viewer "GD art" button** (on by default when served by `tools/serve.js`, with "game look" on):
  objects as GD's sprites, tinted by the level's colour channels at that moment (header + colour
  triggers, `lib/look.js`), in GD's z-layers and z-order, with glow; background (`game_bg_NN`, header
  `kA6`), middleground (`fg_NN` + `fg_NN_2`, `kA25`), ground (`groundSquare_NN` + `_2`, `kA7`), floor line
  (`floorLine_0N`, `kA17`), the player icon of each mode (icon 1, the user's lime/cyan). Ids with no
  known frame fall back to the shape drawing; "GD art" off = the shapes of `lib/look.js` as before.
  Off on `file://` and on the phone page (`tools/web.js` strips it; see "Phone").
- `lib/art.js` -- plist parser (TexturePacker format 3), object -> sprite tree, tinting (multiply on a
  cached canvas per frame and colour), drawing, scenery, icons. Tree part runs in node.
- `lib/objects_art.js` (generated by `tools/import_art.js`) -- OpenGD's object table, GD 2.1, 1541 ids
  up to 1910: root frame, child sprites (frame, offset, rotation, scale, flip, z, anchor), colour role
  per sprite (base = main channel, detail = detail channel, black = 1010), default z-layer, z-order,
  main/detail channels; plus the 12 glow frames of `GameObject::getGlowFrame`.
- `lib/objects_frames.js` (generated by `tools/import_frames.js`) -- GD 2.2's OWN id -> root frame
  table, 4093 ids (1..4539), read out of the user's `GeometryDash.exe` (ObjectToolbox's init is a long
  run of `mov [rbp+x], id ; lea rdx, "frame.png" ; call`). Agrees with OpenGD on 1434 of 1541 ids; the
  rest are objects whose root sprite GD swaps in setup (OpenGD has the swapped one), so OpenGD wins
  where it has the id. For 2.2-only ids we know the root frame only: no children, layer T1, channel 1004.
- `tests/art_tables.js` -- plist parsing, trees, and every named frame exists in the install's sheets.
- **`tools/shoot.js`** -- pictures of a level as GD draws it, no browser to drive: headless Edge renders
  1920x1080 frames at given level times into `local/shots/<level>/` (`--at 2,5.5`, default every 2 s).
  `<level>` = a .gdlvl, `local/official_NN.json`, `official:9`, or `save:<name>` (the copy installed
  in the user's save, read only). `--rec <video> --t0 <s>`: render | game side by side. The viewer's
  `?shoot=<job>` mode does the drawing (no overlays, camera snapped); `tools/headless.js` is shared with
  `tools/catalogue.js`. Then Read the PNGs. A few seconds for a few frames once the level is solved.

- **Deco catalogue**: `tools/catalogue.js` + `viewer/catalogue.html` + `lib/catalogue.js` (group, family,
  note per id) -> `knowledge/objects/` (catalogue.tsv, usage.json, README.md) and `local/catalogue/*.png`.

- **`lib/vfx.js` -- GD 2.2's visual triggers** (viewer with GD art, and shoot.js): fires every trigger
  from the replay path (x crossing, spawn chains with delays, multi-activate loops) and gives, at any
  time: colour (spawn-fired too; copy colour + HSV; player colours), pulse on channels and groups (fade
  in / hold / fade out, HSV mode, main / detail only), alpha per group, moves with all easings and the
  lock-to-player x / y parallax moves (58 / 59, multipliers 143 / 144), rotations about a centre group,
  toggles, camera zoom and offset. Objects' own HSV (keys 41-44) in lib/art.js. 30-50 ms to build for
  a 15-75k object rated level. Not yet: area triggers (3006-3024), static camera (1914), camera rotate
  (2015), follow / advanced follow (1347 / 3016), particles (2065, key 145 holds the emitter settings),
  shaders (2904-2924), animated objects (1585), counters / events / collision triggers, stop (1616).
- **Trigger ids by GD's own button frames** (catalogue.tsv, group "triggers"): 899 colour, 1006 pulse,
  1007 alpha, 901 move, 1346 rotate, 1049 toggle, 1268 spawn, 1585 animate, 1913 zoom, 1914 static,
  1916 offset, 2015 camera rotate, 2062 edge, 2065 particles, 2903 gradient, 2904-2924 shaders (shock
  wave, shock line, glitch, chromatic, chromatic glitch, pixelate, lens circle, radial / motion blur,
  bulge, pinch, grayscale, sepia, invert, hue, edit colour, split screen), 3006-3024 area / enter
  triggers, 3016 advanced follow, 3022 teleport, 3029 change bg, 3031 change mg, 3600 end, 3602 SFX,
  3604 event, 3610 damage square, 3642 BPM guide, 1612 hide player, 1520 shake.

- **Deco kit for composing: `tools/vfxkit.js`** (gd-style calls it from make.js; this session owns it):
  `parallax(sections, opts)` -> two background layers per section (far: art clouds / clouds / hexagons /
  cartwheels / spirals by the section's kind, 3x, B4, darkened by object HSV; near: 1.8x, B3), each a
  group moved by a lock-to-player-x trigger (0.9 / 0.6 of the player's motion) and faded in / out at its
  section's edges; `beatPulses(sections, grid, opts)` -> pulse triggers on bar starts in the section's
  light channel, a strong background + light flash on `flash` sections and `opts.drops`. ~0.6 objects
  per block on GDLM 45's look test. Try it on any level: `node tools/vfxkit.js <level.gdlvl>` (sections
  from its portals) -> local/tmp/<name>_kit.gdlvl, then shoot.js. Checked in our render only, not yet
  in the user's game (lock-to-player duration and multiplier semantics are from the rated levels' data).

- **Level map: `tools/levelmap.js <level> [--brief briefs/NN.json] [--shapes] [--rows N] [--scale s]`**
  -- the whole level as one picture in stacked rows (2400 px wide, ~0.5 px per unit), GD art (or
  `--shapes`), each 600-unit chunk drawn at the moment the player passes it (colours, moved objects),
  with the replayed path over it: mode colours, a dot per press, a hollow square where a hold is let go,
  yellow diamonds at orbs / pads, portal names (short, stacked when crowded), seconds and % ticks,
  section names from a brief (blocks, or beats on its grid), and a red X with the reason where the run
  stops. Uses a solution saved on today's physics (official levels: theirs), else solves fresh (a stale
  one died in GDLM 45's wave). Writes local/maps/<name>.png + .jpg (phone, <= 1600 px); the viewer's
  "level map" button opens the .jpg. GD-art maps and official levels stay local; `_shapes` maps are
  art-free (for the phone page, gd-sync). Drawn by the viewer's map mode (`mapRender`, `MAPCAM`).

- **Signature: `tools/signature.js`** (the user's idea, 2026-11-23: a robot and a human side by side,
  "Made by Claude (and some humans)", at the end of every level; v2 the same day after "Can we improve the
  signage in the end"). A robot and a human high-fiving on a small lit stage (a plinth with a glowing
  edge), a spark where the hands meet, a spotlight (two 1293 gradients) and a dim halo (497) behind them,
  and two text lines: "MADE BY CLAUDE" (gold, 0.62) over "(and some humans)" (white 1011, 0.4). On each
  beat heard in the last ~26 blocks: both hop 4 units (901), the spark and the stage edge flash (1006),
  the spotlight breathes every other beat. API: `header(h, opts)` puts its 12 channels (988-999) in the
  level header, `signature({col, floorY, shirt:[r,g,b], beats, period, xOfT, tOfX, group0=960, ch0=988})`
  returns ~140 objects + beat triggers, `describe(desc)`. make.js does all three for every GDLM level
  (shirt = the last section's light colour, beats from the song grid).
  **Lesson (v1 in the user's phone editor, hellgate v12):** channels set only by colour triggers show in
  the editor as its own pale, see-through placeholder colours -- the editor runs no triggers. Any colour
  a decoration must have from the first frame belongs in the header (kS38). Also channel 1010 is listed
  white in our header template (lib/gd.js), so it is no "black" in the editor; use an own dark channel.
  Not checked yet: the v2 look in the editor and the game (GD's font size and the 1293 / 497 light).
  Try: `node tools/signature.js <level>` -> local/tmp/<name>_sig.gdlvl (replaces an older signature),
  then `node tools/shoot.js` on it.

## Player motion and icons (soft rule: match the game, checked against a recording)

Each mode is drawn with its own icon: GD art -- the user's icon sheets (/gdres/icons); robot and spider built
from their parts as GD's own `Robot_AnimDesc.plist` / `Spider_AnimDesc.plist` place them (run on the ground,
jump going up, fall coming down; 24 frames a second; read at run time, never copied). Shapes look: a drawn shape
per mode in lib/look.js (cube, ship, UFO, ball, wave, robot with striding legs, spider with four legs, swing
with fins). Mini: 0.6 size. Upside down: every icon but the wave's mirrored top to bottom.
Rotation as drawn (viewer visualRot; the sim's own s.rot spins every mode but the ship in the air, which its
hitbox needs, not what the game shows):

| mode | drawn | checked against the game |
|---|---|---|
| cube | spins in the air, lands square | yes (jump arc, PHYSICS.md) |
| ship | tilts with its velocity | by eye in recordings |
| wave | points along its velocity | by eye |
| ball | rolls with distance (one turn per 2 pi x 15 units), direction by gravity | no |
| UFO | nearly level: a quarter of the ship's tilt | no -- the user missed a tilt, then noticed half of it as too much; set from a clean UFO clip when one exists |
| swing | tilts with its velocity | no |
| robot, spider | upright; the legs move | no |

Open: measure the UFO, swing and ball rotation in a recording (track.py on a clean stretch) and set the
factors from it.

## Viewer speed (the user: playback "slightly laggy", 2026-11-23)

Key **F** shows frames a second and the median draw time in the clock line (never over the playfield).
Measured draw() CPU time on GDLM 51 adrift (3173 objects), 120 frames through the level (browser pane, PC):

| canvas | GD art | shapes |
|---|---|---|
| 1009 x 460 | median 2.7 ms, p90 4.0, max 12.9 | median 1.3, p90 2.6, max 14.3 |
| 2400 x 1100 | median 2.5 ms, p90 5.5, max 12.6 | median 1.2, p90 1.8, max 6.2 |

The strip, the button band and the click-table rows each cost < 0.03 ms a frame. So drawing fits a 60 fps frame
(16.7 ms) with room; the occasional 12-14 ms frame is the first draw after a seek (colour timeline, sprite tints).
What was made smooth: the replay used to take the song's AudioContext clock as its time every frame; that clock
moves in steps (a render quantum, ~3-10 ms), so the motion stuttered. Now it advances by frame time and pulls a
tenth of the gap to the song clock a frame. Measured with real frames (tools/perf.js, headless Edge, software canvas, 1896x460) on GDLM 45 wip v8, 3085 objects,
2026-11-23: shapes + beats 60.1 fps, frame p50 16.7 / p99 16.8 ms, 0 frames over 33 ms, draw p50 1.9 / p90 2.9 ms;
light the same (60.1 fps, draw 2.1 ms). GD art + beats: no result (the run timed out loading the sprite sheets
headless -- open). The PC then had ~0.5 GB RAM free with GD and other sessions' jobs (this run waited 49 min for the
heavy slot): the lag the user saw fits the machine, not the viewer.
Big levels (official 22 Dash: 18329 objects, 3792 moved by triggers; "dash is really laggy", 2026-11-24): the
viewer now culls -- static objects from an x-sorted index, a moved object only when its swept x range (sampled
once per level) reaches the view, original order kept; and in GD-art mode it no longer poses every mover for
nothing (the VFX path rebuilt the list anyway). draw() on Dash at t 10 s, before -> after: shapes p50 11.7 -> 5.7 ms,
p90 14.1 -> 10 ms; GD-art setting p50 7.2 -> 5.8, p90 12.9 -> 7.8; posing 4.9 -> 1.5 ms a frame; ~2600 of 18329
objects looked at. The picture is the same (culled vs all differ as much as two draws of the same frame).
**light** (header button, remembered): GD art and beat lines off in one press, for a slow moment.
`node tools/perf.js <level as #lv=> [--at s] [--secs n]` measures playback with real animation frames in headless
Edge (no GPU: a worst case) in three setups -- GD art + beats, shapes + beats, light -- via the viewer's ?perf=
mode (POST /perf -> local/perf/). Not measured yet: real frame rate with the pane visible (the
browser pane here was hidden, so no animation frames ran) and on the phone -- read them with F.

## Facts (checked against the user's recordings)

How: viewer "compare" panel, level start offset set by eye, "save comparison" -> `local/shots/`.
Driven from the browser console: load a level (`load(name, levelStr, solution)` -- officials from
`../local/official_NN.json`), set `cmpRec`, `cmpT0`, `t`, then `cmpShot()`.

- Cycles (official 9) vs `GD claude-rec 2026-11-22_19-09-46.mkv` (attempt 2 starts at 0.9 s), level t=3.2:
  blocks, spikes, chains, ground spikes, orb, portal and ground match (shot
  `local/shots/cmp 2026-11-23T01-24-52-969Z.png`).
- GDLM 41 vs `18-48-19.mkv` (attempt 1 at 7.62 s): the recording shows the level as of commit
  6a9b8b0 (125 objects; the repo and the save now hold a later 95-object version -- identical to each
  other). `node tools/shoot.js local/tmp/gdlm41_v1.gdlvl --rec "GD claude-rec 2026-11-22_18-48-19.mkv"
  --t0 7.62 --at 5.4,6.6` (after `git show 6a9b8b0:levels/gdlm_41_classic.gdlvl > local/tmp/gdlm41_v1.gdlvl`):
  layout, antennas, crystals, background, hills, grid blocks and ground match.
- **Channels 1005/1006 are the player's own colours** whatever the header stores (GDLM 41's header
  says orange for 1005; its P1 deco is lime in the game). They **blend (additive) by default**: Cycles'
  old header has no flag and its ground spikes and chains show lime added over purple (yellowish).
- **Ground spikes 18-21, chains, antennas' balls default to 1005** (OpenGD), confirmed by the colours above.
- **Background**: the 2048 px tile is drawn at natural size (512 units), bottom on the ground line.
- **Background 13 (`game_bg_13`) is a flat white texture** (mean grey 255; the others 140-166), so with it
  the background shows channel 1000 exactly as set -- the one to use for bright / pastel levels (gd-style,
  GDLM 47).
- **Middleground**: only the top ~40 units of the `fg` pictures show above the ground; the rest is under it.
- **Glow** takes the object's main colour (OpenGD; Cycles' white blocks glow white).
- **Rotated frames**: the plist `textureRect` size is the upright size; the sheet holds it turned 90
  degrees clockwise (w and h swapped). Getting this wrong squashed `rod_02`.
- **Portals**: front and back halves are separate frames (`portal_NN_front`, `_back`), each with its own
  trim offset; both centred on the object give the full oval seen in the game.
- **Copy-colour channels** (header kS38 field 9 = the channel copied, 10 = an HSV shift; rated 2.2
  levels use them for glows that follow the background, often blending with an opacity): resolved after
  triggers and pulses every frame (LOOK.applyCopies). Spire attempt 4 (recording 03-23-46, video 86.3 s;
  `local/shots/spire_att4b/`) went from a white-washed screen to the game's green section with it.
  Still lighter than the game overall; the colour change at t 18 comes a bit early.
- Old-format headers (official levels in `local/`): `kS29` bg, `kS30` ground, `kS31` line, `kS32` obj,
  `kS33..36` colours 1-4, `kS37` 3DL; `kS38` field 4 is read as "player colour 1/2" (not verified).

## Phone

The phone page must not carry RobTop's art. Options (not built): (a) the user picks the sheets from the
phone's own GD install once ("add art", like "add song"), kept in that browser's IndexedDB; (b) the PC
renders per-level preview frames into `local/` and the phone page fetches them only from the user's own
machine (needs the PC on). Until then the phone page stays shape-drawn (PHONE.md). Level maps go there only as `--shapes` maps (PHONE.md "Level map").

## How to update

- After a GD update: `node tools/import_frames.js` (re-reads the exe), `node tests/art_tables.js`.
- OpenGD table: see the top of `tools/import_art.js` (clone OpenGD to a scratch folder, run it on it).
- Not used, on purpose: GDRWeb (MIT, but its README forbids use for AI level generation or modification,
  which is what this project does) and GDWeb (CC BY-NC-ND).
